## 4. Provider facts (from knowledge of GitHub REST v3 and Linear GraphQL; no network; live tests confirm)

**GitHub auth and headers.** `Authorization: Bearer <token>` (or `token <token>`), `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, a `User-Agent` (required). Rate limit 5 000 req/h per token (`X-RateLimit-Remaining`, `X-RateLimit-Reset`); mutations are also subject to secondary limits (space writes ≥ 1 s apart; honour `Retry-After`).

**Fine-grained PAT permissions the connect flow must require** (repository permissions; names as the settings UI and `X-Accepted-GitHub-Permissions` spell them): `contents: write` (push a `brahma/` branch), `pull_requests: write` (open PR, merge PR, PR comments), `issues: read` (import) or `issues: write` (sync-back comments; PR comments also route through the issues comment endpoint `POST /repos/{o}/{r}/issues/{n}/comments`), `checks: read` (check runs), `metadata: read` (always granted, read-only), and `commit_statuses: read` if required checks are classic statuses. **`workflows: write` is needed to push a commit that adds or changes `.github/workflows/*`** — without it GitHub refuses the push ("refusing to allow a Personal Access Token to create or update workflow"), which is defence in depth under the plan's `touchesWorkflows` ask. **Scope read-back**: there is no REST endpoint listing a fine-grained token's permissions (classic PATs return `X-OAuth-Scopes`; fine-grained do not). Verify by probing: `GET /user` (identity), `GET /repos/{o}/{r}` (metadata; `permissions { admin, maintain, push, triage, pull }` are the *user's* repo rights, not the token's), and on any 403 read the `X-Accepted-GitHub-Permissions` response header (e.g. `contents=write`). Recommend recording the token owner's `login` and treating the first live push/PR as the scope test, failing closed on 403.

**`GET /repos/{o}/{r}`**: `visibility: "public" | "private" | "internal"`, `private: Bool`, `default_branch`, `allow_merge_commit`, `allow_squash_merge`, `allow_rebase_merge`, `allow_auto_merge`, `delete_branch_on_merge`, `archived`, `permissions {…}`. The plan's rule "public = `visibility != "private"`" (internal counts as not private) — read fresh per push.

**`GET /repos/{o}/{r}/pulls/{n}`**: `number, state (open|closed), merged: Bool, merged_at, merge_commit_sha, head { ref, sha, repo }, base { ref, sha }, draft, mergeable: Bool? (null while GitHub computes — re-GET after a few seconds; never decide on null), mergeable_state`. **Exact `mergeable_state` values**: `clean`, `blocked` (required checks/reviews/rules unmet), `behind` (base moved; strict status checks), `dirty` (conflicts), `unstable` (mergeable but a non-required check failed/pending), `unknown` (still computing), `has_hooks` (pre-receive hooks pending), `draft`. Treat only `clean` (and, per owner policy, `unstable`) as mergeable; `behind` needs a re-push of a re-rebased verified SHA (never "update branch" on GitHub).

**`GET /repos/{o}/{r}/commits/{sha}/check-runs`**: query `per_page` (≤ 100), `page`, `check_name`, `status`, `filter=latest|all` (default `latest`); pagination through the `Link` header (`rel="next"`), `total_count` in the body. Each `check_runs[]`: `id, name, head_sha, status (queued|in_progress|completed; newer: waiting|requested|pending), conclusion (success|failure|neutral|cancelled|skipped|timed_out|action_required|stale|startup_failure|null), started_at, completed_at, html_url, details_url, external_id, app { slug, name }, output { title, summary, text, annotations_count }`. `output.text` is agent-hostile text (EXTERNAL; cap and redact). Classic commit statuses are a different surface: `GET /repos/{o}/{r}/commits/{ref}/status` → `state (success|pending|failure|error)`, `statuses[] { context, state, description, target_url }`; a required check may be either kind, so read both or rely on `mergeable_state == "blocked"` as the arbiter. Branch protection itself (`GET /repos/{o}/{r}/branches/{b}/protection`) needs repository **administration: read** — do not require it; rulesets are readable at `GET /repos/{o}/{r}/rules/branches/{b}` with read access (verify live). The engine never writes protection or rules.

**`GET /repos/{o}/{r}/pulls/{n}/reviews`** (paginated): `id, user { login, id, type }, body, state (APPROVED|CHANGES_REQUESTED|COMMENTED|DISMISSED|PENDING), commit_id, submitted_at, author_association (OWNER|MEMBER|COLLABORATOR|CONTRIBUTOR|FIRST_TIME_CONTRIBUTOR|FIRST_TIMER|NONE|MANNEQUIN), html_url`. An approval counts only when `commit_id == head.sha` (stale approvals may or may not be dismissed depending on the repository's "dismiss stale reviews" setting).

**`GET /repos/{o}/{r}/commits/{sha}`**: `sha, parents [{ sha }], commit { author { name, email, date }, committer {…}, message, verification { verified: Bool, reason, signature, payload, verified_at } }, author: { login, id, type } | null, committer | null`. **`author.login` is null** when the author email is not linked to a GitHub account, and when non-null it is derived from the (forgeable) author email — trust only with `commit.verification.verified == true` (`reason == "valid"`). Commits made through the GitHub web UI (merge button, web edits) are signed by GitHub and verify as `valid`. `reason` values include `valid, unsigned, unknown_key, bad_email, unverified_email, expired_key, not_signing_key, gpgverify_error, gpgverify_unavailable, unknown_signature_type, no_user, malformed_signature, invalid, bad_cert, ocsp_pending`.

**`GET /repos/{o}/{r}/commits/{sha}/pulls`**: the PRs that contain the commit: `number, state, merged_at, merge_commit_sha, base { ref, sha }, head { ref, sha }` (paginated). **`GET /repos/{o}/{r}/branches/{branch}`**: `name, commit { sha, url }, protected, protection { … }, protection_url`. **`GET /repos/{o}/{r}/pulls?head=<owner>:<ref>&base=<b>&state=all`** lists PRs for a head (`head` must be `user:ref` / `org:ref`; empty array when none). **`POST /repos/{o}/{r}/pulls`** body `{ title, head, base, body, draft, maintainer_can_modify }` → 201 `{ number, html_url, head { sha }, node_id }`; 422 when a PR for that head/base already exists or no commits differ. Body limit 65 536 characters. **`PUT /repos/{o}/{r}/pulls/{n}/merge`** body `{ commit_title?, commit_message?, sha, merge_method: "merge" | "squash" | "rebase" }` → 200 `{ sha, merged: true, message }`; **405** "Pull Request is not mergeable" (protection/rules/checks; also when the method is disallowed in some cases — 422 otherwise); **409** "Head branch was modified. Review and try the merge again." (`sha` ≠ head); 403/404 on missing permission. Pick `merge_method` from the repo's `allow_*` flags (prefer `merge` when allowed, else `squash`, else `rebase`); `sha` is always the pushed verified SHA. **`PATCH /repos/{o}/{r}/pulls/{n}`** `{ state: "closed" }` closes without merging. Comments: **`POST /repos/{o}/{r}/issues/{n}/comments`** `{ body }` → 201 `{ id, html_url }` (works for issues and PRs).

**`GET /repos/{o}/{r}/issues?labels=<a,b>&state=open&since=<ISO-8601>&sort=updated&direction=asc&per_page=100`**: returns issues **and pull requests**; skip entries that have a `pull_request` key. Fields: `number, id, node_id, title, body (String?; ≤ 65 536 chars), user { login, id, type }, author_association, state, state_reason, labels [{ name }], assignees, created_at, updated_at, closed_at, html_url`. `since` filters `updated_at >= since` (inclusive) → the cursor must dedupe by `(number, updated_at)`; label filter is AND over the comma list. `GET /repos/{o}/{r}/issues/{n}` for one; `GET /repos/{o}/{r}/issues/{n}/comments` for comments (`user.login, body, created_at`), each EXTERNAL unless the author is listed.

**Edits.** REST **does not expose body edits**: `GET /repos/{o}/{r}/issues/{n}/timeline` (events: `renamed, labeled, unlabeled, assigned, commented, cross-referenced, referenced, closed, reopened, locked, …`) has no `edited` event for the body; only GraphQL `Issue.userContentEdits { nodes { editor { login } editedAt deletedAt diff } }` (and `IssueComment.userContentEdits`) shows who edited. **Recommended simplest safe rule for X8 (matches the plan's controller call "an edited trusted issue drops to untrusted")**: at import, `originTrusted = trust.isTrusted(login: user.login)`; record a hash of `(title, body)` with the item; on every poll where the issue's `updated_at` moved, re-fetch and if the hash changed set `originTrusted = false`, `taintedOrigin = true`, and post a work notice naming `github issue #n (edited)`. A trusted author's own edit also drops trust (cannot be told apart without GraphQL) — acceptable; the owner can re-trust by re-adding nothing, since trust is per login and the item's trust is per snapshot. Collaborators with triage can edit others' issues, hence the rule.

**`GET /user`**: `login, id, node_id, type (User|Bot|Organization), name, email?` — the connecting account; works with `metadata: read`. Record `login` at connect time and seed `TrustList.seed(login:)` with it (the plan's route (c) relies on the engine's own `pushedSHA`, never on self-approval, which GitHub forbids for the PR author).

**git over HTTPS with a token, environment-only.** Mechanism: `http.<url>.extraheader` with `AUTHORIZATION: basic <base64("x-access-token:" + token)>` (any username works for a PAT; `x-access-token` is what Actions/`actions/checkout` use). Key it to the URL so it is sent only to GitHub: `http.https://github.com/.extraheader`. Passed through the environment (git ≥ 2.31): `GIT_CONFIG_COUNT=1`, `GIT_CONFIG_KEY_0=http.https://github.com/.extraheader`, `GIT_CONFIG_VALUE_0=AUTHORIZATION: basic …` — same precedence as `-c`, never in argv, never in a file. ## 5. Stop-rule assessment (brief Step 2)

**Answer: yes — the engine can run `git push` so the token enters only the child's environment, with one additive change.**

- The spawn API that takes an explicit environment exists twice: `ProcessGroupChild.spawn(executable:arguments:environment:workingDirectory:output:stdin:stderr:newSession:workingDirectoryFD:observer:)` `Sources/BrahmaCore/Verify/ProcessGroup.swift:58` (`posix_spawn` with exactly `environment` as `envp`, `:113`) and Foundation `Process.environment` in `GitCommand.runOnce` `Sources/BrahmaCore/Git/GitWorkspace.swift:460`. A test fake of `GitProcessRunning` sees the exact `env`, so "token only in the child env, never in argv" is directly assertable (`args` must not contain it; `env["GIT_CONFIG_VALUE_0"]` must).
- The token never has to touch `ProcessInfo.processInfo.environment`: `GitCommand.environment()` builds the child env from `ChildEnvironment.make(base:)` (allowlist, `TurnProfile.swift:453`) plus `extraEnvironment`, inside the engine, per call. Nothing in the chain writes the env to a file or log (`spawnObserver` receives executable + argv only, `:455`; stdout/stderr files hold git's output only).
- **The one gap**: `GitCommand.environment()` deliberately deletes `GIT_CONFIG_COUNT` and `GIT_CONFIG_PARAMETERS` at `:294-296`, so a credential handed in through `extraEnvironment` as `GIT_CONFIG_COUNT/KEY_0/VALUE_0` would be stripped before the spawn, and the only surviving way to add config today is `extraConfig` → argv (`:301-305`), which is what the stop rule forbids (visible in `ps`). Task 2 must add an additive seam in `GitCommand` — e.g. `var credentialEnvironment: [String: String] = [:]` applied after the strip loop (and only when `allowsHTTPSFetch`), or a `GitPushEnvironment` type that `LiveGitRunner` merges last — and `TokenHandle.inject(into:)` writes exactly the three `GIT_CONFIG_*` variables there. This is a ~5-line change in `GitWorkspace.swift` plus a test proving `GIT_CONFIG_COUNT` still cannot be inherited from the engine's own environment (the base allowlist already excludes it).
- No helper process exists (S absent), so the push runs as a child of the engine, same uid; the plan's `ps eww` red-team item is a residual on every profile but Sandboxed (see §4). The stop rule as written ("hand the token to the child's env only") is satisfiable; **not stopping**.
