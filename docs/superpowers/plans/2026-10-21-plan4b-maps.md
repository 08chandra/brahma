# Plan 4b — Brahma Live Org Chart (Agent Map) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Mission control's AGENT MAP panel becomes a live **org chart**: a top-down tree from the owner ("Board") through the CEO, C-suite, directors and managers down to ICs, grouped by team. It has:
- live state colors and the current work item on every card;
- message edges and traveling particles drawn along or across the tree;
- collapsible subtrees, collapsed below directors by default at scale;
- search and jump, zoom-to-fit and follow-agent;
- vacancy placeholders for open headcount;
- dotted-line review relationships;
- animated hires, terminations and reorgs;
- a one-hour replay scrubber and a pop-out window;
- a `--map-demo` synthetic 300-agent company.

It stays smooth at 300 agents with bursts of 50 messages/s. Everything renders from a reusable, mode-agnostic `MapModel`, so Plan 4c can add the Hive (3D) and Village (2D) renderers without changing it.

**Architecture:** Three layers, the same split Plan 2 uses.
- **`BrahmaCore`** gets read-only, company-scoped feed queries (message flows with recipients, hand-off flows, event ranges), owner add/remove methods over 3a's existing `orgVacancy` table, which is the single source of open headcount (v2 C-12), and a `public init` for `Agent` (the one change to 3a's model types).
- **`BrahmaAppModel`** holds everything testable without rendering. The pure value types are `MapGrouping`, `OrgTree`, `OrgLayout`, `MapModel` (state, diffs, edges, cards, a throttled visual-event queue) and `MapTimeline`. On top of them sits a `@MainActor @Observable MapController`, which polls its own cursors, holds camera, follow, search and replay state, and can run on a synthetic source.
- **`BrahmaMapKit`**, a new library target, renders the org chart with SpriteKit (`OrgScene`) and holds the offscreen snapshotter and the bench. Because it is a library, render smoke tests and perf runs happen under `swift test`.
- **`BrahmaApp`** hosts the scene in SwiftUI with overlays (hover card, team card, scrubber) and a pop-out window.

Optional people data (trust, perks, meter, extra dotted lines) comes in through a `MapPeopleProviding` hook. It is nil in this plan, so nothing depends on Plan 3b, and the chart shows those fields only when a provider supplies them.

**Tech Stack:** Swift 6.2 toolchain (manifest stays `swift-tools-version: 6.0`, `.macOS(.v14)`), SwiftPM, GRDB.swift 7.x, swift-argument-parser 1.5+, Swift Testing, SwiftUI/Observation, SpriteKit (including `SKRenderer`), Metal (offscreen rendering only), CoreText/CoreGraphics (label textures). No third-party assets or packages.

**Decisions this plan pins (with reasons):**
- **Rendering lives in a library target, `BrahmaMapKit`.** Executable targets can't be imported by tests. As a library, scene construction, hit tests, pooling and offscreen PNG snapshots all run under `swift test`, and Plan 4c adds its scenes there.
- **SpriteKit with pooled sprites and cached label textures.** The org chart uses no `SKShapeNode` per agent, because shape nodes are slow at 300 nodes. Cards, labels and particles are `SKSpriteNode`s; text is drawn once with CoreText into cached textures.
- **One color source.** `ThemeHex` (in `BrahmaAppModel`, `UInt32` values) holds every token from the design brief. Both `BrahmaTheme`'s SwiftUI colors and `MapPalette`'s `NSColor`s are built from it, so map colors can't drift from the app.
- **The map polls its own cursors.** It reads the message rowid and the hand-off rowid every 500 ms, and only while a map is visible. It does this because `ActivityEvent.message` rows carry no recipients, so it reads `message` joined with `channelMember` instead. State changes, hires, terminations and reorgs come from diffing `Snapshot.agents`, which `AppModel` already refreshes whenever events arrive.
- **Message semantics on the map:**
  - a DM goes agent → agent; owner DMs start or end at the Board card (an agent's `showAnswer` DM to the owner draws to Board);
  - a channel post goes to each @mentioned agent, capped at 12;
  - any other channel post is a broadcast pulse at the sender, or at the team's manager card for `team-<t>` channels;
  - thread replies (`parentId` set) and the `share`, `showRequest`, `showAnswer` and `fileAsk` kinds are drawn like ordinary posts and DMs;
  - `system` traffic is not drawn: rows whose `senderId = 'system'` or `kind = 'system'` (engine notices, thread-cap notes, concierge answers) are excluded in SQL (Task 1a);
  - **a message counts once** toward the message rate (aggregate mode) however many arrows it fans out into. Visual events, `ingested`, `coalesced` and edge weights count arrows (one per recipient).
- **Open headcount is 3a's `orgVacancy`** (v2 §4.5.2, C-12). 3a records vacancies at company creation (seats beyond the seat budget and trigger-staffed roles), reserves their handles, and fills them with `fillVacancy(companyId:handle:)` / `brahma org fill`. 4b adds only owner-side `addVacancy` / `removeVacancy` over that table (plus a `note` column), the chart's context menu (Add vacancy, Fill, Remove) and the drawing. There is no separate `opening` table. A later plan can feed more vacancies (3b staffing requests) through `MapPeopleProviding.vacancies`; those are tagged `VacancySource.provider`, drawn but **never actionable**: only `.org` vacancies can be filled or removed from the map, and a provider id that equals an org handle is dropped.
- **Dotted lines in 4b are review relationships:** reviewer → owner on 3a items that are `inProgress` or `inReview`. Pairing navigators (3b) arrive only through the provider's `dotted`.
- **Meetings** come from 3a sprints (`Snapshot.work.openSprints`, so no extra query):
  - a sprint in `pendingApproval` shows a planning hull around its team, titled `SPRINT <number> PLANNING` (3a's `Sprint.name` uppercased);
  - a sprint in `review` shows a review hull around its team.

  The Idea review (3b) is left to the provider hook. Replay doesn't reconstruct meetings.
- **Mode** is `MapMode` with the single case `org` in 4b. It is stored per company (`UserDefaults` key `brahma.map.mode.<companyId>`) so 4c's toggle persists from day one. The header shows no toggle while there is only one case.
- **Snapshot PNGs** go to `.superpowers/maps/` and `.superpowers/ui/`. Both are gitignored, as Plan 2's are, and reviewers read them locally.
- **Agent-written text is redacted, then cleaned, before it is drawn.** 5-lite redacts messages, activity, asks, hand-offs and the like at write time, but not work-item titles or blocker reasons (`Blocker.owner(reason:)` is stored raw). `MapController.sync` runs both through `Store.redactor` before they reach `MapInputs`; `MapModel` then applies `MapText.clean` to every string. Vacancy notes are redacted when written (Task 1b) and are owner-only.
- **A restore or a company switch invalidates the controller.** `AppModel.closeStore()` (the in-app restore) and `selectCompany` invalidate a live `MapController` and clear it, so the next one starts with cursors at the current database max. As a second layer, `poll` re-seeds when the database max falls below a cursor. The `run/restored-at` marker is not read (the Orchestrator deletes it on its first tick). An invalidated controller refuses every write (Task 7b).
- **The demo map is read-only.** A synthetic controller has no Store: it offers no write actions, its write methods throw, and its clicks never change `AppModel`'s selection.
- **Fill needs a confirmation.** Filling a vacancy hires an agent that runs paid turns, so the app only reaches it through `FillVacancySheet` (role, manager, team, company and the paid-agent line). The CLI's `brahma org fill` is unchanged.
- **`Agent` gets a `public init`** (Task 5), the only BrahmaCore model change: production code in `BrahmaAppModel` (the synthetic company) must build agents, and 3a's memberwise init is internal. `Sprint` needs none: synthetic meetings are built directly.
- **Execution order:** 1a, 1b, 2, 3, 4, 5, 6, 7a, 7b, 8, 9a, 9b, 10a, 10b, 11 (Task 8 can run any time after Task 2).

## Review Focus

1. **Agent text that breaks labels or leaks secrets**: a role, team name, item title or blocker reason with newlines, bidi overrides (U+202A–U+202E, U+2066–U+2069, U+061C), U+2028/2029, zero-width or tag characters, a 5 000-mark "Zalgo" cluster, 10 000 characters, only whitespace, or an API key an agent echoed. It renders as one capped line with no reordering, emoji joiners survive, empty text becomes `—`, and a secret shows as `[redacted NAME]`. → Task 2 `MapTextTests.*`; Task 4 `MapModelTests.hoverCardTextIsClean`, `teamCardTextIsClean`; Task 7a `MapControllerTests.itemAndBlockerRedacted`; Task 1b `VacancyTests.noteIsRedacted`.
2. **A burst far beyond budget**: 2 000 messages in one poll, or one `#general` post mentioning 300 agents. The queue stays ≤ 400, active events ≤ 150, fan-out ≤ 12 plus one broadcast, structural events are never dropped, the message rate counts each message once, no frame does unbounded work, edge weights still reflect the volume, and every ingested event is accounted for. → Task 5 `MapQueueTests.burstOf2000StaysBounded`, `mentionStormFansOutCapped`, `rateCountsMessagesOnce`, `structuralNeverDropped`, `everyEventAccounted`.
3. **The world changes under the map**: an agent is killed or reorged while a particle is in flight to it; a subtree collapses mid-flight; the company switches mid-poll or with a vacancy sheet open; the database is restored from a backup while the app runs (rowids renumbered or rewound); a stale poll result arrives late. Events for unknown agents are dropped, in-flight particles retarget to the nearest visible ancestor, the old controller is invalidated, stale results are discarded, stale writes are refused, and a restore starts a fresh controller (and a cursor above the DB max re-seeds). → Task 4 `eventsForUnknownAgentsDropped`; Task 9b `inFlightParticleRetargetsOnCollapse`; Task 7a `selectCompanyStopsOldControllerAndDropsStaleResults`, `closeStoreDropsControllerAndReseeds`, `cursorAboveMaxReseeds`; Task 7b `companySwitchRefusesWritesAndDismissesSheet`.
4. **Replay edge cases**: an agent hired mid-window, killed mid-window, or reorged mid-window (reorgs are not replayed, so the current tree is shown and the README says so); the recovery text `"running -> ready (recovered)"`; unparseable state text; more than 20 000 messages; an empty hour. States rewind correctly, absent agents are hidden, the timeline is marked truncated, and an empty hour shows the current state. → Task 6 `MapTimelineTests.*`.
5. **Odd orgs and odd money-moving clicks**: zero agents, all agents killed, one agent, no managers at all (a company made before 3a, where every agent is a root), several roots, a manager cycle in hand-edited data, a 500-agent generated org, a vacancy under a killed manager; and Fill or Remove aimed at a provider-supplied id or from the demo. Layouts never overlap, roots hang under Board with the CEO first, a cycle is broken deterministically instead of looping, default collapse keeps the chart readable, an orphaned vacancy hangs under Board, only an `.org` vacancy can be filled and only after the confirmation sheet, and the demo cannot write. → Task 3 `OrgTreeTests.*`; Task 7b `providerVacancyCannotBeFilledOrRemoved`, `syntheticWritesRefused`, `fillPreviewShowsRoleAndCost`.

### Task 1a: Core map feed queries

**Files:**
- Create: `Sources/BrahmaCore/Store/Store+MapFeed.swift`
- Test: `Tests/BrahmaCoreTests/MapFeedTests.swift`

**Interfaces:**
- Consumes: Plan 1's `message`, `channel`, `channelMember` and `activityEvent` tables; Collab-MVP's `message.kind` (`text|share|showRequest|showAnswer|fileAsk|system`) and `message.parentId` columns (`"vC-refs"`, `"vC-threads"`); `MessageRouter.mentions(in:)` (internal, same module); 3a's `handoff` table (`toAgentId`) and `WorkItem.key`. An agent's handle is `Agent.name`.
- Produces:
  - `public struct MessageFlow: Equatable, Sendable { var rowId: Int64; var messageId, companyId, senderId /* agent id | "owner" */, channelId, channelName: String; var channelKind: ChannelKind; var kind: String /* the message.kind text */; var recipientIds: [String]; var team: String?; var createdAt: Date }`:
    - DM: `recipientIds` = the channel's other members (agent ids or `"owner"`).
    - Channel: the non-killed company agents whose handle is @mentioned, excluding the sender, in mention order.
    - `team` = `t` when the channel name is `team-<t>`.
    - Thread replies (`parentId != nil`) are ordinary rows and resolve exactly like posts in their channel or DM. `share`, `showRequest`, `showAnswer` and `fileAsk` rows are ordinary traffic too.
    - **System traffic is excluded in SQL:** rows with `senderId = 'system'` or `kind = 'system'` never appear in any feed query, so `senderId` is never `"system"` here.
  - `public struct HandoffFlow: Equatable, Sendable { var rowId: Int64; var id, itemKey, authorId: String; var toAgentId: String?; var createdAt: Date }`
  - `Store` feed queries. **Every one filters by `companyId`**: rowids are global across companies, and the handle → id map, the DM memberships and the mention resolution are built from that company's rows only.
